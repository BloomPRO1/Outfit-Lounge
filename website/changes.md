- **Bug found and fixed during verification — DATE column timezone shift**: the local Postgres server's `DATE` columns (`start_date`/`end_date`) were coming back from `pg` as JS `Date` objects at local midnight; since this machine's timezone is `Asia/Colombo` (UTC+5:30), serializing them with `res.json()` (which calls `toISOString()`) silently shifted every date **one day earlier** in UTC (e.g. a promotion stored as `2026-07-08` was returned to the frontend as `"2026-07-07T18:30:00.000Z"`). This didn't affect discount eligibility (that check runs as `CURRENT_DATE BETWEEN ...` inside SQL, never touching JS Date), but it corrupted every displayed date (admin list, public promotions page) by one day, and — worse — would have silently shifted a promotion's date range one day earlier every time an admin re-saved it via the edit form (which pre-fills from the wrong displayed date). Fixed in `website/backend/src/db/pool.ts` with a `pg` type parser override for the `DATE` OID (1082) that returns the raw `"YYYY-MM-DD"` string unchanged, bypassing JS Date conversion entirely.
